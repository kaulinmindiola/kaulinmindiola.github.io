Kafka se cae después de crear la orden

Kafka goes down after the order is created

La orden y su evento se guardan en la misma transacción (Transactional Outbox). Con Kafka caído las órdenes se aceptan y esperan en PostgreSQL; al volver, se publican solas.

The order and its event are stored in the same transaction (Transactional Outbox). With Kafka down, orders are still accepted and wait in PostgreSQL; when it returns, they publish on their own.

Alguien reutiliza un refresh token viejo

Someone reuses an old refresh token

Cada refresh entrega un token nuevo e invalida el anterior. Si un token ya usado aparece de nuevo, es señal de robo: se revoca toda la sesión.

Every refresh issues a new token and retires the previous one. If an already used token shows up again, it signals theft: the whole session is revoked.

A payment engine that moves money correctly under concurrency, retries and partial failures: internal and external transfers against an unreliable provider.

Decisiones técnicas

Technical decisions

  • Bloqueo pesimista con orden determinista de bloqueos: sin actualizaciones perdidas ni deadlocks.
  • Doble idempotencia: reclamo en Redis y restricción UNIQUE en PostgreSQL como respaldo.
  • Resilience4j: reintentos y circuit breaker solo en fallos técnicos; un rechazo de negocio nunca se reintenta.
  • Arquitectura hexagonal verificada con ArchUnit en cada build.
  • Pessimistic locking with a deterministic lock order: no lost updates, no deadlocks.
  • Dual idempotency: a Redis claim with a PostgreSQL UNIQUE constraint as backstop.
  • Resilience4j: retries and circuit breaker only on technical failures; a business decline is never retried.
  • Hexagonal architecture enforced with ArchUnit on every build.

Relay · Resilient Order Pipeline

Flujo de órdenes entre dos servicios, sin transacciones distribuidas: crear la orden es síncrono; reservar inventario y confirmarla ocurre de forma asíncrona.

An order flow between two services without distributed transactions: creating the order is synchronous; reserving stock and confirming it happens asynchronously.

Decisiones técnicas

Technical decisions

  • Transactional Outbox en ambos servicios: se evita la doble escritura base de datos + Kafka.
  • Consumidores idempotentes: entrega at-least-once, con efecto de negocio una sola vez.
  • Reintentos con backoff y Dead Letter Topics; los mensajes inválidos no se reintentan ni bloquean al resto.
  • Reserva de stock sin sobreventa ni deadlocks bajo concurrencia.
  • Transactional Outbox in both services: avoids the database + Kafka dual write.
  • Idempotent consumers: at-least-once delivery, with the business effect applied once.
  • Retries with backoff and Dead Letter Topics; invalid messages are never retried and never block the rest.
  • Stock reservation without overselling or deadlocks under concurrency.
